# 业务主流程与性能优先设计指导：以 Pinning 改造为例

## 远端 pin 是尽力而为的备份

租约有效期间，worker 按策略、可用配额和重试预算尝试 pin。`one` 和 `all` 决定尝试哪些 provider，不承诺每个文件在某个时限内至少有一份远端副本。文件可以在排队中到期，一次也没有提交；这不影响已发布的 S3 对象，也不算 pin 成功。

租约到期、取消或被驱逐时，撤回它对各目标的需求。尚未发出的提交不再派发，也不为这笔租约补做重试或切换 provider。若同一 `(provider, CID)` 仍有其他有效引用，就保留已有 pin。最后一个引用结束后，只清理可能已经产生的远端资源：从未发出的请求无需远端 unpin；已发出但结果未知的请求保留记录，按原路由核对，迟到的成功回执用于回收，不会复活租约。Kubo 接受 `pin/rm` 即完成 unpin，块何时释放由 GC 决定；整个过程不删除 S3 对象或主节点副本。

## 主动取块的提交响应模式

原生 Kubo 的 CID 提交由后台保持 `pin/add` 请求，普通任务不等它的 HTTP 回执。收到与目标 CID 匹配的成功响应后记录结果，不追加 `pin/ls`、DAG 回读或完整性查询。超时保留为结果未知，不把本地派发算成已 pin，也不盲目重发。

其他 provider 按各自协议区分已受理与已完成。`upload` 和 `CAR` 仍执行各自所需的数据传输与校验。
