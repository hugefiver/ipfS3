# Local identities, policy and temporary credentials

Manage users and bucket policy in gateway configuration. Existing static keys keep their access and persistent owner identity when no applicable policy is configured. Use an immutable in-process policy evaluated at request boundaries: stable subject, operation, bucket, key/prefix, requested version, and applicable request/existing object tag conditions. Explicit denial takes precedence; a policy-managed user needs a matching allow. Bucket restrictions apply to matching callers. Unsupported configuration fails at load. When a condition needs existing tags, evaluate the version and tags from the business operation's selected snapshot or affected mutation boundary, including implicit current-version reads. Serve or mutate that authorized selection rather than resolving current again. No access-decision ledger or background reconciliation.

An offline command emits AWS credential_process Version 1 credentials for a configured user and duration. Gateways sharing configuration verify signed sessions locally. A fresh temporary key ID, a domain-separated HMAC-derived secret and an authenticated token binding the ID, configured subject and expiration allow s3s to perform normal SigV4 verification. Use a dedicated signing secret. Static keys remain distinct from temporary keys. For temporary keys validate the accompanying standard signed header or presigned query token once, using the verified key ID. Pass the stable subject to subsequent operations. No HTTP STS or IAM management service.

Apply authorization to standard S3 and authenticated custom routes before side effects. Use actual sources and destinations for Copy, individual batch-delete items, bucket prefixes and exact versions; handle custom import, ZIP publication scope, ordinary and ZIP MPU completion, pin and task status. An output-prefix reservation authorizes that whole scope, not a single representative key. Retain existing behavior for unconfigured static credentials, including signing and unsigned preflight behavior. No blanket object-tag fetch for permission checks or per-item policy checks on listings.

Verify a configured user and its issued temporary credentials through the signed service, including presigned access, different permissions on shared buckets, tag/version decisions, and rejected or expired sessions without side effects. Preserve existing unconfigured S3 flows; no provider or database call to issue or verify a session.
